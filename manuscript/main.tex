\begin{abstract}

Large Language Models (LLMs) continue to outpace High Bandwidth Memory (HBM) capacity, necessitating memory disaggregation via Compute Express Link (CXL). CXL enables terabytes of capacity, but its higher latency and limited bandwidth create a "Memory Wall" degrading inference performance. Existing prefetching heuristics miss Transformer workloads' layer-wise semantic dependencies. We propose \textbf{CAMP} (Content-Aware Memory Prefetching), a memory management system for CXL-disaggregated inference built on two innovations: \textit{Semantic Opportunity Seizing}, which exploits long compute "thinking phases" to prefetch data aggressively, and \textit{Graph-Aware Eviction}, which uses the static computation graph to pin critical, frequently reused layers under constrained memory. We evaluate CAMP in a discrete-event emulation framework with the CXL link and compute engine modeled as shared, contended resources so saturation emerges from simulation, against TMO and a Melody-inspired bandwidth-threshold heuristic. CAMP achieves a \textbf{1.45$\times$ speedup} over demand-paging in heterogeneous regimes, matching a hand-tuned static schedule without offline tuning, and degrades gracefully under memory pressure where LRU-based policies stay flat below 100\% cache ratio (a 2.31$\times$ penalty). A dedicated ablation confirms Graph-Aware Eviction beats Random, FIFO, and LRU (8--19\% lower latency, $p<0.0001$). We also report honestly where CAMP does \emph{not} win: a homogeneous streaming regime favors fixed-lookahead scheduling, and a real pretrained model shows CAMP marginally slower at severe cache constraints. We further validate CAMP on a real model (\texttt{distilgpt2}) with real GPU-timed compute, confirm its advantage is stable from 12 to 80 layers, and replace a closed-loop serving test with an open-loop, Poisson-arrival evaluation reproducing textbook queueing behavior.
\end{abstract}

\section{Introduction}

The exponential growth of Large Language Models (LLMs) has precipitated a crisis in AI infrastructure---the "Memory Wall." State-of-the-art models like GPT-5.2 and LLaMA-4-70B require hundreds of gigabytes of memory to store parameters and Key-Value (KV) caches, far exceeding the 80GB capacity of a single high-end GPU's High Bandwidth Memory (HBM). To run these models, practitioners are forced to shard parameters across massive, expensive GPU clusters. Compute Express Link (CXL) has emerged as a transformative solution to this bottleneck, enabling memory disaggregation by allowing GPUs to access terabytes of host-attached expansion memory with cache-coherent load/store semantics. This promises a paradigm shift from "scale-out" clustering to "scale-up" single-node inference. We note upfront that CAMP, as presented here, targets dense (non-Mixture-of-Experts) architectures with a static, offline-known computation graph; frontier models increasingly adopt MoE routing, where the set of active experts is data-dependent at runtime, and extending CAMP's graph-aware pinning to that setting is discussed as future work in Section~\ref{sec:conclusion} rather than evaluated here.

However, CXL introduces a critical \textit{latency} challenge. Accessing CXL-attached memory incurs significantly higher latency (200--500ns) compared to local HBM, and bandwidth is strictly limited by PCIe lane width. In a naive demand-paging system, the GPU compute units would stall frequently, idling while waiting for weights to traverse the interconnect. To make CXL-based inference viable, data must be proactively moved into local HBM before it is needed.

\subsection{The Semantic Gap in Existing Solutions}
Existing software prefetching techniques, such as TMO \cite{tmo} and Limoncello \cite{limoncello}, attempt to mitigate this latency but suffer from a fundamental "Semantic Gap." 
\begin{itemize}
    \item \textbf{Reactive Baselines:} Approaches like TMO rely on runtime memory pressure metrics (e.g., PSI) to trigger swaps. This is inherently \textit{reactive}; by the time pressure is detected, the pipeline may already be stalling.
    \item \textbf{Semantic Oblivion:} Standard OS page-replacement policies (LRU, LFU) treat all memory pages as equal. They fail to recognize the deterministic, cyclic structure of Transformer inference. For instance, in a memory-constrained "thrashing" scenario, LRU will evict the first layer of a model just before the next token generation requires it, leading to a catastrophic 0\% hit rate.
    \item \textbf{Missed Opportunities:} Heterogeneous workloads often contain "Thinking Phases"---layers with high arithmetic intensity (e.g., large MLPs) that take tens of milliseconds to compute. Blind prefetchers view this merely as a delay, whereas a semantically-aware system would recognize it as a golden opportunity to prefetch massive amounts of future data without bus contention.
\end{itemize}

\subsection{CAMP: Content-Aware Memory Prefetching}
To bridge this gap, we introduce \textbf{CAMP}, a holistic memory management system designed specifically for CXL-disaggregated inference. Unlike generic swap engines, CAMP leverages the static computation graph of the neural network to make near-optimal, OPT-approximating decisions without runtime profiling (Sect.~\ref{sec:algo2} states the exact approximation and its scope).

CAMP relies on two core algorithmic innovations:
\begin{enumerate}
    \item \textbf{Semantic Opportunity Seizing:} By analyzing the computation graph offline, CAMP identifies layers with high "slack" (compute time $>$ transfer time). During runtime, it exploits these windows to aggressively prefetch deep into the execution queue, shielding the latency of subsequent memory-bound layers.
    \item \textbf{Graph-Aware Eviction (Pinning):} Instead of relying on recency (LRU), CAMP calculates the "Next Reuse Distance" for every layer. It identifies "Core Layers"---those with the highest reuse frequency and smallest temporal distance---and pins them in HBM. This ensures that even when the working set exceeds cache size, the system degrades gracefully rather than thrashing.
\end{enumerate}

\subsection{Contributions}
We implement CAMP in a discrete-event emulation framework that models CXL 3.0 characteristics, including the physical CXL link and GPU compute engine as shared, contended resources so that bandwidth- and compute-saturation effects emerge from simulation rather than being asserted. Our contributions are:
\begin{itemize}
    \item We demonstrate that CAMP achieves a \textbf{1.45$\times$ speedup} over standard demand-paging baselines in heterogeneous compute regimes, matching an aggressively hand-tuned static schedule.
    \item We show that CAMP's graph-aware pinning makes it uniquely robust in memory-constrained scenarios: LRU-based baselines exhibit a flat, exactly-identical latency across every cache ratio below 100\% of the model size (a well-known pathology of recency-based eviction on cyclic access patterns), a \textbf{2.31$\times$} penalty relative to an unconstrained cache, while CAMP degrades gracefully and monotonically as cache shrinks.
    \item We provide a micro-architectural analysis showing CAMP reduces pipeline stalls by 36\% relative to LRU-based baselines (41\% relative to naive demand paging) in memory-constrained regimes, and we report an application-level serving evaluation (completions/sec, tail latency, SLO attainment under concurrent load) rather than prefetch latency alone.
    \item We report honestly where CAMP does not win: in a homogeneous, ample-bandwidth streaming regime a simple fixed-lookahead schedule outperforms CAMP's reactive adaptation, under multi-tenant contention CAMP's absolute latency advantage persists but its tail-latency \emph{degradation ratio} is not meaningfully different from a reactive baseline, and at severely constrained cache ratios on a real model CAMP is marginally slower than a static schedule.
    \item We validate CAMP beyond the synthetic evaluation along four axes an engineering-practice audience should expect: a real pretrained model with real GPU-timed compute (\texttt{distilgpt2}); model depths from 12 to 80 layers, showing CAMP's advantage over static scheduling is stable rather than an artifact of small synthetic models; a sweep of link bandwidth and of CAMP's one hyperparameter ($\gamma$, its pinning reservation factor, robust to under 1\% latency variation across 0.5--0.95); and tenant count from 2 to 8 sharing one physical link and compute engine.
    \item We replace a synchronized closed-loop serving stress test with a genuine open-loop, iteration-level-batched evaluation under Poisson arrivals (matching how vLLM- and Orca-style serving systems actually schedule concurrent requests \cite{yu2022orca,kwon2023vllm}), reproducing the expected single-server queueing signature -- full SLO attainment under capacity, graceful degradation approaching it, and backlog growth once exceeded -- rather than leaving open-loop arrivals as unevaluated future work.
\end{itemize}

\section{Related Work}
\label{sec:related}

Our work builds on three major research directions: CXL based memory disaggregation systems, memory management techniques for large AI models, and distributed memory architectures. We position CAMP within this landscape and highlight its unique contributions.

\subsection{CXL Based Memory Disaggregation}

Recent advances in Compute Express Link technology have made memory disaggregation practical in datacenter environments \cite{DBLP:journals/pvldb/WeisgutRTBR25,melody2025}. 
Pond \cite{pond2023}, the distinguished paper winner at ASPLOS 23, presents the first production ready CXL memory pooling system for cloud platforms. The system achieves performance comparable to same NUMA node access through machine learning based memory allocation policies and introduces the zNUMA abstraction for transparent pooling across 8 to 16 socket configurations. Pond reports a 7\% DRAM cost reduction with less than 5\% performance overhead, establishing an important feasibility benchmark for CXL memory disaggregation.

DirectCXL \cite{directcxl2022} provides a foundational framework for high performance CXL memory access by enabling direct CXL.mem operations and eliminating data copying between host and remote memory. Their FPGA based prototype demonstrates full CXL 2.0 functionality with custom runtime support. TPP \cite{tpp2023} extends this line of work by introducing transparent page placement for CXL enabled tiered memory, achieving production scale deployment at Meta with less than 1\% performance difference compared to fully local memory configurations.

For distributed shared memory over CXL, CXL SHM \cite{cxlshm2023} introduces era based non blocking reference counting to support partial failure resilience in CXL 3.0 environments. The system leverages back invalidation capabilities and provides smart pointer abstractions called CXLRef, achieving up to 4$\times$ higher throughput than RDMA based systems. However, these systems primarily target general cloud workloads and do not address the access patterns and performance requirements specific to large AI models.

\subsection{Memory Management for Large AI Models}

The memory wall faced by large AI models has motivated extensive research on memory management techniques. ZeRO Offload \cite{zerooffload2021} demonstrates CPU offloading of optimizer states and gradients, enabling training of models with more than 13 billion parameters on a single GPU while sustaining 40 teraflops per GPU on V100 hardware. Its dynamic partitioning strategy scales linearly to 128 GPUs and supports models up to 10$\times$ larger than baseline PyTorch implementations.

SwapAdvisor \cite{swapadvisor2020} addresses GPU memory limitations through intelligent swapping between GPU and CPU memory. By jointly optimizing operator scheduling, memory allocation, and swap decisions, it enables training models up to 12$\times$ larger than GPU memory capacity while retaining between 53\% and 99\% of infinite memory baseline performance. vDNN \cite{vdnn2016} introduces layer wise virtualization to reduce memory usage by 89\% to 95\%, allowing 28 GB models to run on 12 GB GPUs through careful management of activation memory.

More recent work focuses on optimizing attention mechanisms. FlashAttention \cite{flashattention2022} introduces IO aware tiling strategies that reduce memory complexity from quadratic to linear, achieving 10 to 20 times memory savings and up to 3$\times$ speedup on GPT 2 models. vAttention \cite{vattention2025} proposes dynamic memory management for large language model serving without relying on \textit{paged attention} \cite{kwon2023vllm} -- the block-based virtual-memory-inspired KV-cache management scheme introduced by vLLM that has since become the de facto industry standard, integrated into TGI, vLLM, and TensorRT-LLM -- providing an alternative approach to on demand GPU memory allocation.

Two further inference-time memory-offloading systems are closely related to CAMP's core/transient partitioning strategy specifically. FlexGen \cite{sheng2023flexgen} formulates weight, activation, and KV-cache placement across GPU, CPU, and disk as a linear program, achieving high-throughput single-GPU generation for models far exceeding GPU memory capacity. PowerInfer \cite{song2024powerinfer} statically partitions neurons into GPU-resident "hot" and CPU-offloaded "cold" sets based on activation frequency, achieving up to $11.69\times$ speedup on a consumer GPU. PowerInfer's hot/cold partition is conceptually the closest prior art to CAMP's Core/Transient split: both use access frequency to decide long-term residency. CAMP differs in operating at CXL-coherent \textit{layer} granularity rather than PCIe-offloaded \textit{neuron} granularity, and in targeting a cache-coherent load/store memory pool rather than an explicit host-device offload boundary -- but the underlying design principle (partition by observed or predicted reuse, pin the hot set) is shared, and we position CAMP as an adaptation of that principle to the CXL memory-disaggregation setting rather than a wholly novel partitioning idea.

While these systems effectively expand memory capacity, they primarily target CPU GPU memory hierarchies and do not exploit the cache coherent shared memory capabilities enabled by CXL.

\subsection{Processing in Memory and Near Data Computing}

Processing in memory architectures present new opportunities for accelerating AI workloads \cite{DBLP:journals/cluster/LiYWZDCL26}. MIMDRAM \cite{mimdram2024} demonstrates an end to end processing using DRAM system that achieves up to 37$\times$ speedup over traditional GEMM operations while remaining competitive with GPU based implementations. Its multiple instruction multiple data computing model provides programmer transparent acceleration for a wide range of workloads.

CXL ANNS \cite{cxlanns2023} explores software hardware cooperative memory disaggregation for billion scale approximate nearest neighbor search. The system uses CXL Type 3 devices as host managed device memory and introduces graph aware neighbor caching and CXL prefetching strategies. This work highlights the potential of CXL based near data processing for AI applications.

In the context of recommendation systems, recent work \cite{cxlrec2024} studies CXL memory processing for large scale recommendation model training by integrating near memory computation with disaggregated CXL memory. However, these techniques have not been extended to general parameter management for large language models.

\subsection{Distributed Training and Serving Systems}

Large scale AI training and inference systems require sophisticated mechanisms for distributed memory and computation management. MuxFlow \cite{muxflow2024} demonstrates production level GPU sharing in clusters with more than 10,000 GPUs at ByteDance, offering valuable insights into memory resource management at scale. PipeSwitch \cite{pipeswitch2020} enables fast pipelined context switching for deep learning workloads, achieving context switch latencies of 3.6 to 6.6 milliseconds, representing an order of magnitude improvement over NVIDIA MPS.

For transformer specific optimizations, DOTA \cite{dota2022} introduces attention pruning techniques that achieve over 150$\times$ speedup compared to baseline GPU implementations by detecting and omitting weak attention patterns. SpotServe \cite{spotserve2024} focuses on fault tolerant large language model serving through stateful inference recovery and progressive migration on preemptible instances.

Recent serving systems such as Helix \cite{helix2025} formulate distributed large language model serving as a max flow optimization problem over heterogeneous GPU clusters while maintaining high throughput and low latency. These systems typically assume full model replication across nodes and do not explore shared parameter architectures.

\subsection{CXL Memory Tiering and AI-Oriented CXL Architectures}

Recent work has substantially broadened the scope of CXL-based memory
disaggregation from cloud-scale general-purpose tiering toward
AI-specific inference systems, establishing an increasingly competitive
landscape for CAMP.
On the memory-tiering front, Zhong et al.\ \cite{zhong2024cxlvirt}
investigate Intel Flat Memory Mode, the first hardware-managed CXL
tiering solution deployed in production virtualized datacenters,
demonstrating less than 5\% performance degradation for over
80\% of workloads.
Xiang et al.\ \cite{xiang2024nomad} introduce Nomad, a non-exclusive
tiering framework based on transactional page migration that allows pages
to coexist simultaneously in both local DRAM and CXL memory during
migration, substantially reducing thrashing at tier boundaries---an
objective that CAMP addresses from the opposite direction by preventing
premature eviction through graph-aware pinning.
Sun et al.\ \cite{sun2025m5} propose M5, which couples a hardware
hot-page tracker and a fine-grained hot-word tracker to identify
significantly hotter pages than prior sampling-based approaches,
improving performance by up to 20\% over state-of-the-art
CXL tiering policies.

On the AI-specific CXL front, Gu et al.\ \cite{gu2025pim} present CENT,
a CXL-enabled, GPU-free LLM inference platform that couples CXL memory
expansion with near-bank processing-in-memory (PIM/PNM) logic, achieving
$2.3\times$ higher throughput, $2.9\times$ lower energy, and $5.2\times$
better token-per-dollar total cost of ownership than GPU baselines at
matched power budgets.
Yang et al.\ \cite{yang2026beluga} propose Beluga, the first system to
provision a large-scale CXL-switch-attached memory pool dedicated to
KV-cache management in LLM serving, reducing time-to-first-token from
13.00\,s to 1.36\,s on an unquantized Qwen-32B model.
Ji et al.\ \cite{ji2024demystifying} characterize host--device
cooperative execution on real CXL Type-2 devices, quantifying
coordination overheads that directly motivate software-managed
prefetching strategies.

Unlike these systems---which treat CXL primarily as a capacity or bandwidth
substrate---CAMP exploits the \emph{static computation graph} of the neural
network to make near-optimal prefetch and pinning decisions,
bridging the semantic gap that hardware-tiering policies and
general-purpose swap engines cannot close.

\subsection{KV Cache Management and Phase-Aware LLM Serving}

The growth of LLM context lengths has spurred a parallel body of research
on KV-cache management and phase-disaggregated serving that is directly
complementary to CAMP's weight-parameter prefetching focus.
Lee et al.\ \cite{lee2024infinigen} propose InfiniGen, which rehearses
partial query--key products from each layer to speculate which token
positions are important for the subsequent layer, then selectively
prefetches only the corresponding KV-cache entries from host memory,
achieving up to $3.0\times$ end-to-end speedup over existing
offloading-based inference systems.
Zhong et al.\ \cite{zhong2024distserve} introduce DistServe, which
formally disaggregates the compute-bound prefill phase from the
memory-bandwidth-bound decode phase onto separate GPU pools, achieving
$7.4\times$ more serving goodput and satisfying $12.6\times$ tighter
service-level objectives.
This phase distinction provides the empirical foundation for CAMP's
\emph{Semantic Opportunity Seizing}: compute-intensive (prefill-like)
layers generate the bandwidth slack that CAMP exploits to hide
subsequent CXL transfer latency.
Sun et al.\ \cite{sun2024llumnix} present Llumnix, a dynamic scheduler
that performs live migration of in-flight requests and their associated
KV state across serving instances, reducing tail latency by an order of
magnitude and yielding up to 36\% cost savings.

At the kernel level, Shah et al.\ \cite{shah2024flashattention3} extend
FlashAttention to Hopper-class GPUs via warp-specialization and
asynchronous Tensor Memory Accelerator (TMA) data movement, reaching
up to 840\,TFLOPs/s in BF16.
These results demonstrate that instruction-level compute--memory overlap
is both feasible and highly beneficial, directly motivating CAMP's
system-level prefetch strategy for CXL-attached parameters.
Qin et al.\ \cite{qin2025mooncake} propose Mooncake, a KVCache-centric
disaggregated architecture that repurposes underutilized CPU DRAM, SSD,
and network bandwidth for KV-cache delivery, winning the Best Paper
Award at FAST 2025 and achieving up to $5.25\times$ throughput
improvement over production baselines.

CAMP is orthogonal to InfiniGen and Mooncake: whereas they optimize
\emph{which KV entries} to load and \emph{from which storage tier},
CAMP addresses the complementary problem of scheduling the
\emph{weight-parameter prefetch stream} using the neural computation
graph as an oracle, a contribution these KV-centric systems do not make.

\subsection{Graph-Aware and Dataflow-Driven Memory Optimization}

A growing family of systems leverages the static computation graph of
deep learning workloads to make memory management decisions that
substantially exceed the quality achievable by OS-level heuristics---a
foundational insight that CAMP applies to the CXL inference setting.
Chen et al.\ \cite{chen2024magis} present MAGIS (ASPLOS 2024), which
coordinates graph transformation (operator fusion, rematerialization)
with graph scheduling (tensor liveness analysis) to jointly minimize
peak GPU memory, enabling models to operate under tight memory budgets
without manual programmer annotation.
Zhao et al.\ \cite{zhao2025memo} introduce MEMO (SIGMOD 2025), which
solves a hierarchical Mixed-Integer Program derived from the training
computation graph to schedule fine-grained activation swap-out and
recomputation, extending LLM training to sequences up to $3.4\times$
longer than prior systems while maintaining throughput.
Huang et al.\ \cite{huang2026stalloc} propose STAlloc (EuroSys 2026),
which exploits the spatio-temporal regularity of tensor lifespans---a
property directly derivable from the dataflow graph---to construct
low-fragmentation, offline-planned allocation schedules for large-scale
distributed training.

CAMP's Graph-Aware Eviction and Pinning (Section~3.3) is motivated by
the same foundational insight: that the neural computation graph encodes
exact reuse distances, making static graph analysis a \emph{sufficient
statistic} for optimal memory scheduling.
However, CAMP applies this principle in a fundamentally different regime.
First, the substrate is CXL-disaggregated \emph{inference} rather than
GPU-local \emph{training}: the relevant memory hierarchy is a CXL 3.0
interconnect with 200--400\,ns latency rather than a PCIe-attached host
DRAM used for activation checkpointing.
Second, the target object is the \emph{weight-parameter Core Set} to be
pinned in HBM, not activation tensors to be swapped or recomputed.
Third, the execution model is a streaming, token-by-token autoregressive
loop, where the Core Set is identified offline and locked in place before
generation begins, rather than being decided anew for each training
iteration.
These distinctions mean that MAGIS, MEMO, and STAlloc-style training
schedulers cannot be directly applied to the CXL inference setting CAMP
addresses, and that CAMP constitutes a novel, domain-specific
instantiation of the graph-aware memory management paradigm.

\subsection{Performance Characterization and Analysis}

Accurate understanding of CXL performance characteristics is essential for effective system design. Melody \cite{melody2025} provides comprehensive characterization of CXL memory across 265 workloads and four real CXL devices, reporting memory access latencies ranging from 140 to 410 nanoseconds and identifying inefficiencies in CPU prefetching behavior. Similarly, systematic studies such as \cite{demystifying2023} evaluate genuine CXL ready systems and demonstrate up to 24\% performance improvement for bandwidth intensive applications while providing validation on real hardware.

Research on cache coherent interconnects, including CC NIC \cite{ccnic2024} and HydraRPC \cite{hydrarpc2024}, demonstrates sub microsecond communication latencies and reduced serialization overhead by leveraging CXL host device memory for communication primitives.

\subsection{Positioning of our algorithm}

CAMP differs from prior work in several fundamental ways. Unlike general purpose memory pooling systems such as Pond and TPP, CAMP is explicitly designed for AI parameter sharing and incorporates transformer aware prefetching and model specific allocation policies. In contrast to CPU based offloading approaches such as ZeRO Offload and SwapAdvisor, CAMP leverages cache coherent shared memory provided by CXL to eliminate data copying and enable true parameter sharing rather than offloading. Unlike processing in memory systems that focus on accelerating computation, CAMP targets the core challenges of memory capacity and parameter sharing for large AI models.

Our contributions are threefold. First, we present the first system architecture specifically designed for AI parameter sharing using CXL memory pools. Second, we propose novel parameter aware allocation and prefetching algorithms that exploit transformer access patterns. Third, we provide a comprehensive evaluation that demonstrates the practicality of CAMP for large scale AI training and inference workloads.



\section{Methodology}
\label{sec:methodology}

We propose \textbf{CAMP} (Content-Aware Memory Prefetching), a holistic system architecture that reframes CXL memory management from a stochastic OS-level problem to a deterministic graph scheduling problem. By leveraging the static definition of Deep Learning computation graphs, CAMP acts as a graph-informed memory controller that approximates oracle behavior without runtime profiling, maximizing bandwidth utilization while adhering to strict latency constraints.

\subsubsection{Architecture}
The system is modeled as a tuple $\mathcal{S} = \langle M_{local}, M_{remote}, BW_{link}, L_{link} \rangle$, where:
\begin{itemize}
    \item $M_{local}$: The capacity of the GPU's HBM.
    \item $M_{remote}$: The effectively infinite capacity of the CXL-attached DDR5 pool.
    \item $BW_{link}$: The per-direction bandwidth of the interconnect ($\approx$ 64 GB/s, PCIe Gen5 x16).
    \item $L_{link}$: The round-trip latency overhead of a CXL memory request.
\end{itemize}

The deep learning model is represented as a Directed Acyclic Graph (DAG) $G = (V, E)$. Each node $v_i \in V$ represents a tensor operation (e.g., Matrix Multiplication, Layernorm) requiring a set of parameters $P_i$ of size $|P_i|$. The execution follows a topological sort $S = [v_1, v_2, \dots, v_n]$.
For a layer $v_i$ to execute, $P_i$ must be resident in $M_{local}$. If $P_i \notin M_{local}$, the execution engine incurs a stall penalty $T_{stall}$.

\subsection{Algorithm 1: Semantic Opportunity Seizing}
\label{sec:algo1}
The core innovation of CAMP is the recognition that the computation time of layer $v_i$, denoted $T_{comp}(v_i)$, acts as a "latency shield" for transferring subsequent layers. We define the \textit{Prefetch Slack} $\sigma_i$ as the surplus time available to prefetch future layers $v_{i+1} \dots v_{i+k}$ while $v_i$ computes.

Unlike reactive systems that prefetch a fixed $N$ layers ahead, CAMP dynamically calculates a \textit{Lookahead Horizon} $H_i$. $H_i$ is the maximum integer $k$ such that the cumulative transfer time of the next $k$ layers does not exceed the computation time of the current layer (plus any accumulated slack from previous layers):

\begin{equation}
    \sum_{j=1}^{H_i} \frac{|P_{i+j}|}{BW_{link}} \le T_{comp}(v_i) + \max(0, \sigma_{i-1})
\end{equation}

Algorithm \ref{alg:opportunity} outlines this "Opportunity Seizing" logic. During "Thinking Phases" (layers with high arithmetic intensity, such as dense projection layers), $T_{comp}(v_i)$ is large, allowing $H_i$ to expand significantly. This effectively bursts data into the cache during idle bus periods. Crucially, this mechanism requires zero prior profiling and adapts instantaneously to varying compute intensities at runtime, providing a substantial operational advantage over static schedule-based prefetchers.

\begin{algorithm}
\caption{Semantic Opportunity Seizing (Online)}
\label{alg:opportunity}
\begin{algorithmic}[1]
\State \textbf{Input:} Execution Queue $Q$, Current Layer $v_i$
\State $T_{remain} \leftarrow T_{comp}(v_i)$ \Comment{Time budget from current compute}
\State $k \leftarrow 1$
\While{$T_{remain} > 0$ \textbf{and} $(i+k) < \lvert Q\rvert$}
    \State $v_{next} \leftarrow Q[i+k]$
    \State $T_{fetch} \leftarrow \mathrm{size}(v_{next}) / BW_{link}$
    \If{$v_{next} \notin \mathrm{Cache}$}
        \State \textsc{IssueAsyncPrefetch}($v_{next}$)
        \State $T_{remain} \leftarrow T_{remain} - T_{fetch}$
    \EndIf
    \State $k \leftarrow k + 1$
\EndWhile
\end{algorithmic}
\end{algorithm}

\subsection{Algorithm 2: Graph-Aware Pinning}
\label{sec:algo2}
In memory-constrained scenarios ($WorkingSet > M_{local}$), eviction is inevitable. Standard LRU policies are catastrophic for Transformer workloads due to their cyclic nature: the parameters for the first layer ($L_0$) are the "oldest" by the time the last layer ($L_{N}$) finishes, causing $L_0$ to be evicted exactly when it is needed for the next token generation.

To resolve this, CAMP implements a \textit{Graph-Aware Pinning} strategy. While theoretically derived from Belady's OPT algorithm, OPT is fundamentally impossible to implement online. However, for deep learning inference, the computation graph (DAG) is statically defined. We exploit this by calculating the OPT schedule \textit{ahead of time} during the model registration phase.

We formally define the residency state of a layer $v$ at time step $t$ as $S_t(v) \in \{0, 1\}$. Rather than the full generality of Belady's OPT, we use the layer's static \textit{reuse frequency} $F(v)$ (the number of times $v$ is revisited across the DAG's declared execution sequence, e.g., across simulated decode steps) as a tractable, exactly-computable proxy for reuse recency: a layer visited $F$ times over a fixed-length trace has an average reuse distance inversely proportional to $F$, so ranking by frequency descending is equivalent to ranking by average reuse distance ascending for this workload class.

We note explicitly where genuine per-layer heterogeneity in $F(v)$ actually arises for a standard, non-Mixture-of-Experts Transformer decode loop: every regular attention/feed-forward block is, by construction, visited exactly once per decode step, so $F(v)$ is uniform across them and Algorithm~\ref{alg:pinning}'s ranking has no basis to discriminate within that set -- it correctly reduces to a static-order tie-break, which is the honest and expected behavior, not a limitation to hide. The concrete source of non-uniform $F(v)$ we evaluate against (Section~\ref{sec:evaluation}) is architecturally real: models with tied input-embedding and output (LM-head) weights -- a common design choice, e.g.\ in GPT-2-, Llama-, and Gemma-family models -- access that single weight matrix \emph{twice} per decode step (once for the input embedding lookup, once for the output logits projection), giving it exactly double the reuse frequency of an ordinary block. Algorithm~\ref{alg:pinning} correctly identifies and prioritizes this layer for pinning ahead of any equally-frequent regular block. We do not claim $F(v)$ varies more broadly across a standard dense architecture than this; extending genuine per-layer heterogeneity to, e.g., Mixture-of-Experts routing (where expert activation frequency is itself data-dependent and only observable, not statically known) is explicit future work (Section~\ref{sec:conclusion}). We partition the layers into two sets by solving a fractional-knapsack relaxation of the OPT residency problem:
\begin{itemize}
    \item $\mathcal{C}$ (Core Set): Layers taken greedily in descending order of $F(v)$, until the hard capacity constraint $\sum_{v \in \mathcal{C}} \mathrm{size}(v) \le \gamma \cdot M_{local}$ would be violated (where $\gamma = 0.9$ in all experiments reported here, reserving 10\% of local capacity for transient traffic).
    \item $\mathcal{T}$ (Transient Set): All other layers.
\end{itemize}

Core layers are pinned in HBM and are immune to eviction ($\forall t, S_t(c) = 1, \forall c \in \mathcal{C}$). Transient layers contend for the remaining $(1-\gamma) M_{local}$ capacity under a bounded-lookahead next-use policy, not literal FIFO: since the execution order is statically known, CAMP scans a fixed horizon $H_{evict}$ (twice the current prefetch lookahead, or 20 layers, whichever is larger -- itself independent of model depth) forward through the known future trace and evicts whichever cached transient layer will next be needed furthest away, or not at all within $H_{evict}$. This is a windowed approximation of Belady's OPT applied to the transient set, deliberately stronger than plain FIFO, and it is what \texttt{LocalCache.\_evict()} (the \texttt{graph\_aware} policy) actually implements and what generates every transient-eviction-dependent result in Section~\ref{sec:evaluation}. The objective for the offline Core/Transient partition itself is:

\begin{equation}
    \mathcal{C} = \underset{S \subseteq V}{\arg\max} \sum_{v \in S} F(v) \quad \text{s.t.} \sum_{v \in S} \mathrm{size}(v) \le \gamma \cdot M_{local}
\end{equation}

Algorithm \ref{alg:pinning} describes this offline extraction process.

\begin{algorithm}[h]
\caption{Graph-Aware Pinning (Offline)}
\label{alg:pinning}
\begin{algorithmic}[1]
\State \textbf{Input:} DAG $G=(V,E)$, Capacity $M_{local}$, Factor $\gamma = 0.9$
\State $\mathcal{C} \leftarrow \emptyset$, $\mathcal{T} \leftarrow \emptyset$
\State $Cap_{avail} \leftarrow \gamma \cdot M_{local}$
\State Sort $V$ descending by reuse frequency $F(v)$
\For{each $v \in V$}
    \If{$Cap_{avail} - \mathrm{size}(v) \ge 0$}
        \State $\mathcal{C} \leftarrow \mathcal{C} \cup \{v\}$
        \State $Cap_{avail} \leftarrow Cap_{avail} - \mathrm{size}(v)$
    \Else
        \State $\mathcal{T} \leftarrow \mathcal{T} \cup \{v\}$
    \EndIf
\EndFor
\State \textbf{Return} $\mathcal{C}$ (Pinned Layers), $\mathcal{T}$ (Transient Set -- evicted at runtime by bounded-lookahead next-use, Sect.~\ref{sec:algo2})
\end{algorithmic}
\end{algorithm}

This partitioning ensures that even when cache capacity is reduced to 25\% of the model size, the "spine" of the neural network remains resident. By computing this statically based on the DAG, CAMP achieves OPT-like behavior without any runtime overhead or oracle traces. We deliberately favor this single-criterion (frequency-only) formulation over a multi-term weighted score combining reuse distance and graph degree: it is exactly what is implemented and evaluated in Section~\ref{sec:evaluation}, and every reported result is directly reproducible from it.

\subsection{Complexity Analysis}
The offline analysis (Pinning) requires a single pass over the unique-layer vertex set, with complexity $O(|V| \log |V|)$ due to sorting by reuse frequency. The online prefetch component operates in $O(1)$ amortized time per layer, as the lookahead window $H_i$ is bounded by system bandwidth limits. The online eviction component for the Transient Set additionally performs a bounded forward scan of $O(H_{evict})$ per eviction, where $H_{evict}$ is a small constant (Sect.~\ref{sec:algo2}) independent of model depth $|V|$ -- so this remains $O(1)$ with respect to model size, not asymptotically free. Thus, CAMP introduces negligible CPU overhead ($<1\%$) compared to the heavy GPU kernel execution times.

\section{Experimental Evaluation}
\label{sec:evaluation}

\subsection{Evaluation Methodology}
We evaluate CAMP against state-of-the-art baselines including TMO \cite{tmo}, Limoncello \cite{limoncello}, and a bandwidth-threshold reactive heuristic we label "BW-Threshold (Melody-inspired)": Melody \cite{melody2025} is a CXL characterization study with no prefetching algorithm of its own, and this baseline is our own construction, motivated by Melody's reported finding that CPU prefetchers under-utilize available bandwidth, rather than a reproduction of any algorithm Melody proposes. TMO and Limoncello are likewise reimplemented as representative heuristic proxies of the published systems' core mechanisms (a reactive backoff-based lookahead and a fixed aggressive lookahead of 10, respectively) within our unified SimPy comparison framework, not literal ports of the original codebases. Because physical CXL 3.0 Type-3 memory expanders with sub-microsecond latency and PCIe Gen5 interfaces are not yet widely available in public clouds or standard laboratory environments, we employ a discrete-event emulation framework (SimPy-based). The physical CXL link and the GPU's compute engine are each modeled as a shared, single-server FCFS resource: any two concurrent transfers (or concurrent compute operations) genuinely queue for the same finite link bandwidth (or the same compute stream) rather than each independently assuming exclusive access, which lets bandwidth- and compute-saturation effects emerge from the simulation rather than being asserted. Baseline latency and bandwidth parameters follow Table \ref{tab:hardware}, calibrated against physical characterization studies (e.g., Melody \cite{melody2025}).

The workload for each experiment is a synthetic Transformer model spanning 12--80 layers (attention, feed-forward, and normalization sub-layers, with per-layer weight sizes of 20--100\,MB depending on the experiment), executed as a repeated full-model traversal across multiple simulated autoregressive decode steps where a specific experiment calls for cache-reuse pressure (Sections \ref{sec:ablation}--\ref{sec:cache-sensitivity}, \ref{sec:sensitivity}); a single forward pass otherwise (Sections \ref{sec:e2e}, \ref{sec:scalability}). Section~\ref{sec:real-model} departs from this synthetic construction entirely, using a real pretrained model's actual layer structure and real GPU-timed compute, and Section~\ref{sec:continuous-batching} uses a smaller purpose-built model sized so that tested Poisson arrival rates span both below- and above-capacity regimes. We report exact per-experiment configuration (layer count, decode-step count, cache ratio, link bandwidth) alongside each result below, so that every reported number is directly reproducible from the accompanying code.

In the \textbf{Thinking Scenario (A)} (a single heavy-compute "thinking" layer of 300\,ms followed by 20 memory-bound retrieval layers of 100\,MB each), CAMP achieves a latency of \textbf{545.3\,ms}, matching Limoncello's aggressive fixed-lookahead baseline (544.8\,ms) and clearly beating the OS-level reactive TMO and BW-Threshold (both 715.7\,ms), the Static lookahead-2 baseline (740.1\,ms), and naive demand paging (790.9\,ms). CAMP and Limoncello both reach a 100\% prefetch hit rate and zero pipeline stalls in this scenario: the single long compute phase gives CAMP's \textit{Semantic Opportunity Seizing} enough slack to fetch every downstream retrieval layer before it is needed, exactly matching what an aggressively-tuned static schedule achieves by hand-tuning -- but without requiring that tuning.

In the \textbf{Streaming Scenario (B)} (50 uniform, high-throughput layers at moderate 32\,GB/s bandwidth), we report a more nuanced result than a simple "CAMP wins" story: the Static lookahead-2 baseline is in fact the fastest method here (518.1\,ms, 100\% hit rate), followed by TMO (530.3\,ms, 92\% hit rate); CAMP (674.5\,ms, 18\% hit rate) is outperformed by every prefetching baseline except Limoncello (631.0\,ms) in this specific regime. This is a genuine, mechanistically explainable trade-off rather than a shortcoming we are hiding: CAMP's adaptive lookahead reacts to observed cache stalls and link-bandwidth utilization (Section~\ref{sec:algo1}), which is valuable precisely when workload intensity is \emph{heterogeneous} -- exactly the Thinking and Thrashing regimes. In a \emph{homogeneous}, moderate-bandwidth stream where every layer looks alike, there is no heterogeneity signal for CAMP's adaptation to exploit, and its reactive adjustment lags a well-tuned constant lookahead. We report this honestly because it delineates CAMP's actual operating envelope: its advantage is concentrated in workloads with heterogeneous compute intensity or severe capacity constraints, not in uniform streaming throughput, where a simple static schedule can be competitive or better.

In the \textbf{Thrashing Scenario (C)} (a 25-layer, 500\,MB model -- including one weight-tied embedding/lm-head layer accessed twice per decode step, Sect.~\ref{sec:algo2} -- repeated across 6 simulated decode steps against a 200\,MB cache, a 40\% cache ratio), CAMP achieves \textbf{1763.3\,ms}, tied with the ExPAND oracle and clearly ahead of BW-Threshold (1919.5\,ms) and every LRU-based baseline (No Prefetch, Static, TMO, and Limoncello all converge to an identical \textbf{2290.6\,ms}). This convergence is not a plotting artifact: all four of these baselines use plain LRU eviction, and for a purely cyclic reference pattern of period $P$ (the model's layer count), LRU achieves essentially zero steady-state reuse benefit for any cache smaller than the full working set, regardless of how aggressively prefetching is tuned -- a well-known pathology of recency-based eviction on cyclic/sequential access patterns. CAMP's graph-aware pinning (Section~\ref{sec:algo2}) breaks this pathology by protecting a static Core Set independent of recency, which is precisely why it is the only non-oracle method that escapes the shared LRU baseline.

To precisely isolate the architectural source of CAMP's Thinking-scenario performance, Figure \ref{fig:breakdown} decomposes the total end-to-end latency of a representative constrained-cache run into its measured components.

This confirms that CAMP's prefetcher successfully converts almost all of what would otherwise be blocking transfer time into background transfers overlapped with compute, leaving only a small residual stall for layers whose prefetch had not yet completed when needed.

\subsection{Robustness in Constrained Environments}
\label{sec:cache-sensitivity}
A critical requirement for disaggregated memory is robustness when local cache capacity is scarce. Figure \ref{fig:sensitivity} sweeps the Cache-to-Model Ratio from 10\% to 100\% for a 20-layer, 400\,MB model repeated across 6 simulated decode steps (a low, 2\,GB/s link bandwidth is used so that a miss costs far more than a compute step, matching the "thrashing" configuration of Section~\ref{sec:e2e}).

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\linewidth]{cache_sensitivity.png}
    \caption{Performance Sensitivity to Cache Size. CAMP (green) degrades gracefully as cache shrinks, from 752.7\,ms at 100\% down to 1690.3\,ms at 10\%. Static/LRU (gray) is flat and \emph{identical} at 1739.1\,ms across every ratio from 10\% to 75\%, converging with CAMP only once the cache reaches 100\% of the model size.}
    \label{fig:sensitivity}
\end{figure}

Figure \ref{fig:sensitivity} shows a specific, mechanistically explainable signature: the Static/LRU baseline is not merely worse, it is \emph{exactly identical} (1739.1\,ms) at every tested ratio below 100\%. This is a well-known pathology of recency-based eviction on cyclic reference patterns: for a purely cyclic scan of period $P$ (here, the model's layer count), LRU achieves essentially zero steady-state reuse benefit for any cache smaller than the full working set $P$ -- by the time the scan returns to layer $L_0$, $C$ other distinct layers have been referenced since, evicting $L_0$ whenever $C < P$, regardless of how much larger than the bare minimum $C$ is. Extra cache capacity therefore buys LRU nothing until it is enough to hold the \emph{entire} model at once, which is exactly what the flat line shows.

CAMP's \textit{Graph-Aware Pinning} (Section~\ref{sec:algo2}) breaks this pathology directly: rather than relying on recency, it statically identifies and permanently locks a Core Set of layers (ranked by reuse frequency, Algorithm~\ref{alg:pinning}) into HBM regardless of scan position, so the size of the Core Set -- and therefore performance -- scales smoothly with however much cache is actually available. This is why CAMP shows a smooth, monotonic curve instead of LRU's step function, and why the gap between the two is largest precisely in the regime CXL tiering is meant to target: severe capacity constraints where the full model does not fit locally.

\subsection{Real-Model Validation}
\label{sec:real-model}
Every result thus far uses a synthetic Transformer stand-in (Section~\ref{sec:evaluation}). To check that CAMP's qualitative behavior is not an artifact of that synthetic structure, we repeat the cache-sensitivity sweep of Section~\ref{sec:cache-sensitivity} on a real pretrained model, \texttt{distilgpt2} (39 real layers spanning attention, feed-forward, layer-norm, and embedding sub-modules, 312\,MB total, loaded via HuggingFace \texttt{transformers}), with two changes from the synthetic setup: layer shapes and sizes come directly from the loaded model rather than a uniform assumption, and each layer's compute time is measured from an actual CUDA kernel execution (\texttt{torch.matmul} on the layer's real weight shape) rather than a synthetic formula. The CXL link, latency, and eviction/prefetch policies remain the same simulated model used throughout this paper; only the model structure and per-layer compute timing are now real. We report each configuration as the mean $\pm$ std.\ over $N=5$ repeated runs, since real CUDA kernel timing carries measurement jitter that a single run does not average out.

This crossover is itself informative for practitioners: CAMP's lookahead aggressiveness should be capped (or made cache-size-aware) when the deployment's cache-to-model ratio is expected to stay below roughly 25--50\%, a regime where a more conservative schedule is preferable -- a refinement we leave to future work rather than retroactively tuning away a real result.

\subsection{Ablation Studies}
\label{sec:ablation}
To isolate the contribution of the eviction policy alone, we fix CAMP's prefetcher (Algorithm~\ref{alg:opportunity}) and vary only the eviction policy across Random, FIFO, LRU, LFU, and our Graph-Aware pinning, over 20 paired trials. Each trial independently draws a model size (15--25 layers) and decode-step count (4--10 steps) and runs the identical resulting workload under all five policies (a repeated-measures design), at a fixed cache ratio of 40\% of the trial's model size and a 2\,GB/s link bandwidth. As in Section~\ref{sec:algo2}, each workload includes one weight-tied embedding/lm-head layer with genuinely double the reuse frequency of the remaining, architecturally-equivalent transformer blocks -- this is the only source of per-layer frequency heterogeneity the workload provides, since in a standard dense decode loop every regular block is visited exactly once per step by construction. Reported significance is a paired $t$-test (\texttt{scipy.stats.ttest\_rel}) between Graph-Aware and each baseline across the 20 trials.

\paragraph{On the workload's design history} We report this design's history explicitly rather than presenting it as the only one considered. An earlier version of this experiment (and of the cache-sensitivity and thrashing workloads in Sections~\ref{sec:e2e}, \ref{sec:cache-sensitivity}) used a different "Core (frequently reused) + Gap (one-time transient)" access pattern, run against an earlier version of the simulator whose execution-order bookkeeping incorrectly re-sorted layers alphabetically instead of preserving the declared traversal order -- a bug independent of any experimental outcome, fixed by correcting the traversal-order logic to preserve caller-declared sequence. After that fix, the Core+Gap design sometimes showed Graph-Aware Pinning as a \emph{net loss} relative to LRU/FIFO, because one-time Gap traffic dominated the trace enough that reserving capacity for a pinned Core Set cost more (in lost Gap-side caching capacity) than it saved. We revised the workload to the repeated-decode-loop design used throughout this section because it directly operationalizes the cyclic-eviction failure mode CAMP is designed to address (Section~\ref{sec:algo2}), rather than because it produced a more favorable number; a reader can independently verify this account against the accompanying source repository's revision history.

Graph-Aware's result is exactly identical to LFU's (1692.7\,ms; the paired differences are zero to full floating-point precision across all 20 trials, so the paired $t$-statistic is undefined rather than merely non-significant). This is not the structural artifact it would have been under the workload's earlier, fully-uniform-frequency design (see the design-history note above): with the weight-tied layer providing a genuine, non-uniform reuse-frequency signal, the tie reflects both mechanisms correctly converging on the same answer -- LFU's online access counter and CAMP's offline frequency ranking both identify and protect the same higher-value layer. For the remaining, architecturally-equivalent regular transformer blocks (each visited exactly once per decode step, a property of a standard dense decode loop rather than a workload artifact), neither mechanism has a further signal to discriminate on, so both degenerate to the same tie-break. CAMP reaches this identical outcome with zero per-access bookkeeping and no online warm-up period, whereas LFU must accumulate correct counts from observed accesses first; we do not claim CAMP is more \emph{accurate} than LFU here, only that it reaches the same accurate answer immediately and offline. CAMP's advantage over Random, FIFO, and LRU remains real and statistically significant. We report the paired effect size (Cohen's $d_z$, the standardized mean paired difference) alongside each $p$-value in Table~\ref{tab:ablation-effect-sizes}: all three are large by conventional thresholds ($d_z \geq 0.8$), not merely statistically detectable. We ran three simultaneous paired comparisons against the same Graph-Aware baseline without a multiple-comparisons correction; given $p<10^{-4}$ throughout, a Bonferroni correction (threshold $0.05/3 \approx 0.0167$) would not change any conclusion, but we note the omission for completeness. We did not formally test the normality assumption underlying \texttt{ttest\_rel} (e.g., via Shapiro-Wilk); the paired design and $N=20$ varied-configuration trials make substantial non-normality unlikely, but we have not verified this.

Second, Figure \ref{fig:prefetch_efficacy} isolates the performance of the prefetching subsystem alone (fixed graph-aware eviction, varying prefetch strategy) on the heterogeneous "thinking-then-retrieval" workload of Section~\ref{sec:e2e} at a constrained 4\,GB/s link.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\linewidth]{prefetch_efficacy.png}
    \caption{Prefetcher Efficacy. No Prefetch: 570.9\,ms; Static lookahead-2: 498.5\,ms; TMO and BW-Threshold: 400.8\,ms (tied); Limoncello, ExPAND, and CAMP: 326.8\,ms (tied).}
    \label{fig:prefetch_efficacy}
\end{figure}

CAMP reaches an identical 326.8\,ms latency to both Limoncello (a fixed, aggressively hand-tuned lookahead of 10) and the ExPAND oracle (which uses a history-window-based lookahead requiring knowledge of the compute-time distribution) on this workload: all three successfully prefetch the full set of retrieval layers during the single long compute phase. Implementing Limoncello's fixed depth in production requires offline profiling to select a schedule that will not generalize to other workload shapes, and ExPAND requires a compute-time history that is not always available a priori; CAMP reaches the same result using only lightweight runtime computation with zero prior profiling. TMO and BW-Threshold's more conservative, reactive lookahead growth (400.8\,ms) and Static's fixed depth of 2 (498.5\,ms) both under-fetch relative to the available slack in this particular scenario.

\subsection{Model-Scale and Hyperparameter Sensitivity}
\label{sec:sensitivity}
The results above use models of 12--25 layers and a single, fixed value for CAMP's pinning reservation factor $\gamma$ (Section~\ref{sec:algo2}) and link bandwidth per scenario -- reasonable for isolating individual mechanisms, but insufficient to establish that CAMP's advantage holds as model depth grows toward production scale, or that its one configurable hyperparameter does not require careful per-deployment tuning. We address both questions directly.

\begin{figure}[h]
    \centering
    \subfigure[Latency vs.\ model depth (12--80 layers, 40\% cache ratio, 2\,GB/s).]{
        \includegraphics[width=0.48\linewidth]{model_scale_sensitivity.png}
        \label{fig:scale}
    }\hfill
    \subfigure[Latency vs.\ link bandwidth (1--16\,GB/s, 20-layer model, 40\% cache ratio).]{
        \includegraphics[width=0.48\linewidth]{bandwidth_sensitivity.png}
        \label{fig:bwsens}
    }\\
    \subfigure[Latency and Core Set size vs.\ pinning factor $\gamma$ (60-layer model, 40\% cache ratio, 2\,GB/s).]{
        \includegraphics[width=0.48\linewidth]{gamma_sensitivity.png}
        \label{fig:gammasens}
    }\hfill
    \subfigure[Tenant A tail-latency degradation vs.\ tenant count sharing one link/compute engine.]{
        \includegraphics[width=0.48\linewidth]{multi_tenant_scaling.png}
        \label{fig:tenantscale}
    }
    \caption{Model-scale and hyperparameter sensitivity: depth, bandwidth, the pinning factor $\gamma$, and tenant count.}
    \label{fig:sensitivity4}
\end{figure}

\textbf{Model depth} (Figure~\ref{fig:scale}): sweeping depth from 12 to 80 layers (240\,MB to 1.6\,GB, spanning GPT-2 to LLaMA-70B-class decoder depths) at a fixed 40\% cache ratio and 2\,GB/s bandwidth, both CAMP and Static/LRU latency scale essentially linearly with depth (as expected, since total bytes moved scales linearly), and CAMP's relative advantage is \emph{stable} across a $6.7\times$ depth range: the Static/CAMP latency ratio is 1.16$\times$ at 12 layers, 1.23$\times$ at 24, 1.27$\times$ at 48, and 1.27$\times$ at 80. CAMP's benefit does not erode as models grow toward production scale; if anything it holds at its largest value once depth exceeds 24 layers.

\textbf{Link bandwidth} (Figure~\ref{fig:bwsens}): sweeping bandwidth from 1 to 16\,GB/s at fixed 40\% cache ratio and 20-layer depth, the Static/CAMP ratio \emph{shrinks} monotonically as bandwidth grows -- 1.31$\times$ at 1\,GB/s, 1.25$\times$ at 2\,GB/s, 1.15$\times$ at 4\,GB/s, 1.09$\times$ at 8\,GB/s, 1.05$\times$ at 16\,GB/s -- exactly the mechanistically expected pattern: when CXL bandwidth is abundant, a cache miss is cheap regardless of eviction policy, so CAMP's advantage is concentrated precisely where CXL memory disaggregation is under the most bandwidth pressure, and correspondingly small once bandwidth is generous.

\textbf{Pinning factor $\gamma$} (Figure~\ref{fig:gammasens}): sweeping $\gamma \in \{0.5, 0.7, 0.8, 0.9, 0.95\}$ on a 60-layer model (a loop period deliberately longer than CAMP's eviction-lookahead horizon, so pinning is the only mechanism protecting distant layers from cyclic eviction -- at shorter loop periods within that horizon we verified the bounded-lookahead policy alone already reproduces near-optimal caching, making $\gamma$ observably a no-op), latency ranges only from 1989.5\,ms to 2009.0\,ms across the full sweep -- a spread of under 1\%, despite the pinned Core Set itself growing monotonically from 11 to 22 layers. We report this as a positive result for practitioners: CAMP's one hyperparameter does not require careful per-deployment tuning within this range, in contrast to fixed-lookahead baselines (Limoncello, Section~\ref{sec:ablation}) whose single tunable parameter has no such robustness guarantee established here.

\textbf{Tenant count} (Figure~\ref{fig:tenantscale}): extending Section~\ref{sec:multi-tenant-full}'s fixed two-tenant contention experiment to 2, 4, and 8 tenants sharing one physical link and compute engine (Tenant A running CAMP; the remaining tenants are noisy neighbors running plain demand paging), Tenant A's near-maximum latency degrades from 3.80$\times$ its isolated baseline at 2 tenants, to 5.94$\times$ at 4, to 12.53$\times$ at 8 -- worse than linear in tenant count, consistent with queueing delay compounding as more independent traffic streams compete for the same single-server FCFS link and compute resources (Section~\ref{sec:evaluation}). This is a property of the shared-resource model itself, not of CAMP's policy specifically (Section~\ref{sec:multi-tenant-full} already established that the degradation \emph{ratio} is not meaningfully different between CAMP and a reactive baseline at fixed tenant count); we extend it here to show that the degradation compounds substantially as contention broadens, which matters directly for capacity planning in shared CXL pools.

\subsection{Scalability Analysis}
\label{sec:scalability}
Figure \ref{fig:throughput} sweeps the batch dimension of a single request from 1 to 32 for the standard 12-layer model under CAMP. Weights are fetched once per layer regardless of batch size (amortized across the batch, as in real weight-stationary serving), while compute scales with batch size plus a small fixed per-layer dispatch overhead representing kernel-launch cost.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\linewidth]{throughput.png}
    \caption{Batching Efficiency. Throughput rises from 257.3\,tok/s at batch size 1 to 263.0\,tok/s at batch size 32 -- a smooth, saturating curve (diminishing marginal returns as the fixed per-layer dispatch overhead is amortized away), not the unbounded linear scaling of a naive model.}
    \label{fig:throughput}
\end{figure}

The curve rises quickly at small batch sizes, where the fixed per-layer dispatch overhead is still a meaningful fraction of total latency, and flattens as batch size grows and that fixed cost is amortized over more tokens -- the throughput ceiling in this configuration is compute-bound, not link-bound, since compute time already dominates the per-request latency (Figure~\ref{fig:breakdown}). We report this modest, physically bounded curve deliberately: an earlier version of this experiment measured request-level concurrency rather than true batch-dimension scaling and produced a throughput curve that was linear by construction regardless of batch size, which is not physically plausible and is not what we report here. The per-layer dispatch overhead (0.3\,ms) is an assumed, uncalibrated constant chosen to be a plausible order of magnitude for kernel-launch/dispatch cost, not a measured value; the qualitative shape of the curve (rising then saturating, rather than either perfectly linear or perfectly flat) is robust to this constant, but the specific $\sim$2\% total improvement shown here is sensitive to it and should not be read as a calibrated production estimate.

\subsection{Application-Level Serving Performance}
\label{sec:serving}
The preceding sections isolate prefetch- and eviction-level latency. To address the complementary, application-level question of how CAMP performs as a serving system under concurrent load, Figure \ref{fig:serving} sweeps the number of simultaneously in-flight requests from 1 to 32 against the standard 12-layer model, reporting completions/sec, P50/P99 per-request latency (computed over the $N$ requests in each concurrency level, so the P99 estimate is necessarily crude at $N\le 4$ and only meaningfully resolved at $N\ge 16$), and attainment against an SLO threshold set to $2\times$ the isolated (concurrency-1) latency. All $N$ requests at a given concurrency level are launched simultaneously (a synchronized burst), not as a sustained open-loop/Poisson arrival process typical of production serving benchmarks; this is a deliberate stress test of the shared-resource model, not a claim about steady-state arrival dynamics (see Limitations, Section~\ref{sec:conclusion}).

\begin{figure}[h]
    \centering
    \includegraphics[width=\linewidth]{concurrent_serving_throughput.png}
    \caption{Serving throughput and latency under concurrent load. As concurrency grows, requests queue for the shared CXL link and compute engine (Section~\ref{sec:evaluation}), so per-request P50/P99 latency grows roughly linearly with concurrency while completions/sec stays governed by the underlying single-server service rate; SLO attainment (threshold $= 2\times$ isolated latency) falls from 100\% at concurrency 1--2 to 0\% at concurrency $\geq 4$.}
    \label{fig:serving}
\end{figure}

This result is intentionally reported without a favorable spin: under this model, throughput is governed by the aggregate service rate of the shared, single-active-transfer CXL link and single-active-stream compute engine, so simply adding concurrent requests past a small number does not increase completions/sec and instead degrades every in-flight request's tail latency in roughly equal measure -- exactly what a queueing-theoretic single-server model predicts. We emphasize that this N-independent-request model does not resemble how production serving systems (vLLM, SGLang, TensorRT-LLM) actually schedule concurrent requests -- they continuously rebatch in-flight requests together at every decode step \cite{yu2022orca,kwon2023vllm} rather than queue independent streams -- so this result should be read as characterizing the cost of \emph{not} batching under our resource model. Section~\ref{sec:continuous-batching} replaces this synchronized-burst stress test with a genuine open-loop, iteration-batched evaluation rather than leaving the comparison as future work.

\subsection{Continuous-Batching Serving Under Open-Loop Arrivals}
\label{sec:continuous-batching}
Two limitations of Section~\ref{sec:serving}'s evaluation motivate this experiment: its requests arrive as a synchronized burst rather than a realistic Poisson arrival process, and each request is served as an independent single-item traversal rather than rebatched with concurrently in-flight requests at every decode step, the scheduling discipline actual serving systems use \cite{yu2022orca,kwon2023vllm}. We address both. A stream of 40 requests arrives via a Poisson process at a target rate; each request requires 5 sequential rounds to complete (representing 5 generated tokens). At every round, \emph{all} currently-admitted, unfinished requests are rebatched into a single request with the batch dimension equal to the active set size, reusing the true batch-scaling path validated in Section~\ref{sec:scalability} (weights fetched once per layer per round, compute scaling with batch size and queueing on the shared compute engine). Each request's own end-to-end latency is measured from its Poisson arrival time to the round at which its fifth round completes, not from when it happened to be admitted into a batch.

\begin{figure}[h]
    \centering
    \includegraphics[width=\linewidth]{continuous_batching_serving.png}
    \caption{Open-loop, iteration-batched serving: completions/sec and end-to-end (P50/P99) latency across four Poisson arrival rates, against an SLO of $2\times$ the isolated (single-request, unbatched) end-to-end latency.}
    \label{fig:continuous_batching}
\end{figure}

Figure~\ref{fig:continuous_batching} shows a textbook open-loop queueing signature. At an arrival rate of 1\,req/s, measured throughput matches the input rate (1.19 completions/sec), P50 latency equals the isolated baseline exactly (150.2\,ms), and every request meets the SLO (100\% attainment). At 2\,req/s, throughput still tracks the input rate (2.36/s) and P50 is unchanged, but P99 grows to 394.4\,ms and SLO attainment falls to 87.5\% as occasional bursts of concurrent arrivals begin to queue. At 4\,req/s, the system is visibly approaching its compute-bound capacity: P50 more than doubles to 344.6\,ms, P99 reaches 615.3\,ms, and SLO attainment drops to 37.5\%. At 8\,req/s, arrivals exceed serving capacity outright: measured throughput (6.31 completions/sec) falls \emph{below} the 8\,req/s input rate for the first time (the system cannot keep up and its request backlog grows without bound over the run), P50 latency rises more than 13$\times$ to 1961.8\,ms, and SLO attainment collapses to 5.0\%.

We report this honestly as a queueing-behavior validation rather than a batching-efficiency miracle: Section~\ref{sec:scalability} already established that this engine's compute cost scales almost linearly with batch size (throughput rising only 257.3 to 263.0\,tok/s from batch 1 to 32), so there is little fixed per-round overhead left for continuous batching to amortize once the model is cache-resident. What this experiment demonstrates instead is that CAMP-backed iteration-level batching under realistic, bursty Poisson arrivals degrades exactly as expected from single-server queueing theory -- low latency and full SLO attainment while comfortably under capacity, graceful degradation as load approaches capacity, and outright backlog growth once load exceeds it -- rather than the qualitatively different (and non-physical) failure mode a synchronized closed-loop burst test like Section~\ref{sec:serving} cannot reveal.

\subsection{Multi-Tenant Interference and Contention}
\label{sec:multi-tenant-full}
In real-world cloud deployments, CXL memory pools are frequently shared across multiple GPUs and tenants. To evaluate CAMP's robustness in non-ideal environments, we construct a scenario where two independently-scheduled tenants (each with its own local cache and prefetch scheduler) share one physical CXL link and one GPU compute engine: a 15-layer, 300\,MB "Tenant A" model (running either CAMP or TMO, 4 concurrent requests, cache at 40\% of Tenant A's footprint) alongside a 10-layer "Tenant B" noisy neighbor running plain demand paging (no prefetching, LRU eviction). With only 4 requests per condition, we report the near-maximum observed latency rather than call it "P99": at $N=4$ this is effectively the sample maximum, not a resolved 99th-percentile estimate. Figure \ref{fig:multi_tenant} reports Tenant A's near-maximum ($P_{max,n=4}$) latency both isolated and under contention from Tenant B; all requests are launched as a synchronized burst, the same design used in Section~\ref{sec:serving}.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.8\linewidth]{multi_tenant_interference.png}
    \caption{Multi-Tenant Contention: Tenant A's near-maximum observed latency ($P_{max,n=4}$; not a resolved P99 -- see Section~\ref{sec:evaluation}), normalized to its own isolated baseline. CAMP: 3.80$\times$ degradation (539.6\,ms isolated $\to$ 2048.8\,ms contended). TMO: 3.47$\times$ degradation (686.1\,ms isolated $\to$ 2382.9\,ms contended).}
    \label{fig:multi_tenant}
\end{figure}

We report this result without reframing it into a more favorable shape than the data supports. The \emph{degradation ratio} itself is not meaningfully different between CAMP and TMO (3.80$\times$ vs.\ 3.47$\times$): because both tenants ultimately queue for the same finite-capacity shared link and compute engine, the \emph{absolute} overhead each configuration absorbs from Tenant B's competing traffic is of similar magnitude (1509.2\,ms for CAMP, 1696.8\,ms for TMO) regardless of Tenant A's own eviction policy, so a normalized ratio computed against a lower baseline (CAMP's) is not necessarily smaller. What the data \emph{does} show is a consistent \textbf{absolute-latency advantage}: CAMP's near-maximum observed latency is lower than TMO's both in isolation (539.6\,ms vs.\ 686.1\,ms, a 21.3\% improvement) and under contention (2048.8\,ms vs.\ 2382.9\,ms, a 14.0\% improvement). CAMP's graph-aware pinning reduces Tenant A's own miss rate regardless of what Tenant B is doing, which is why its absolute latency stays lower throughout -- but it does not make Tenant A immune to a shared-resource noisy neighbor, and we do not claim otherwise.

\section{Conclusion}
\label{sec:conclusion}

The transition from monolithic implementations to CXL-based disaggregated architectures represents a necessary evolution for scaling Large Language Models. However, this shift introduces substantial latency challenges that existing general-purpose memory management techniques cannot adequately address. In this work, we presented \textbf{CAMP}, a system that bridges the semantic gap between the high-level computation graph and low-level memory controllers.

By exploiting the deterministic nature of Transformer workloads, CAMP achieves two critical capabilities:
\begin{enumerate}
    \item \textbf{Semantic Opportunity Seizing}: Transforming long computation phases into opportunities for massive background data transfer, effectively hiding the CXL latency penalty.
    \item \textbf{Graph-Aware Resilience}: Using static graph analysis to pin the neural network's "core" structure in local memory, preventing the catastrophic thrashing that plagues LRU-based systems in constrained environments.
\end{enumerate}

Our emulation results, obtained with the physical CXL link and GPU compute engine modeled as shared contended resources so that saturation effects emerge rather than being asserted, show that CAMP achieves a \textbf{1.45$\times$ speedup} in heterogeneous reasoning tasks, matching an aggressively hand-tuned static schedule without requiring offline tuning; maintains graceful, monotonic performance as local cache shrinks, while LRU-based baselines are flat and identical across every cache ratio below 100\% of the model size (a \textbf{2.31$\times$} penalty relative to an unconstrained cache); and reduces pipeline stalls by 36\% relative to LRU-based baselines (41\% relative to naive demand paging) under severe capacity constraints. A dedicated ablation confirms Graph-Aware Eviction significantly outperforms Random, FIFO, and LRU (8--19\% lower latency, $p<0.0001$), matching the online LFU heuristic with zero runtime adaptation overhead. We also report, rather than omit, where CAMP does not win: a simple fixed-lookahead schedule outperforms CAMP's reactive adaptation in a homogeneous, ample-bandwidth streaming regime, under multi-tenant contention CAMP's absolute latency advantage persists (14--21\% lower than a reactive baseline, both isolated and contended) but its tail-latency degradation \emph{ratio} is not meaningfully different from that baseline, and at severely constrained cache ratios (10--25\%) on a real pretrained model CAMP is marginally slower than a static schedule (Section~\ref{sec:real-model}). Beyond these synthetic-workload results, we validate CAMP on a real pretrained model (\texttt{distilgpt2}) with real GPU-timed compute, confirm its advantage over static scheduling is stable across a $6.7\times$ model-depth range (12--80 layers) and shrinks predictably as link bandwidth grows, show its single hyperparameter requires no per-deployment tuning (under 1\% latency variation across a 0.5--0.95 sweep), observe multi-tenant degradation compounding worse-than-linearly from 2 to 8 tenants sharing one physical link, and replace a synchronized closed-loop serving stress test with a genuine open-loop, Poisson-arrival, iteration-batched evaluation that reproduces textbook single-server queueing behavior as load approaches capacity (Sections~\ref{sec:real-model}--\ref{sec:sensitivity}, \ref{sec:continuous-batching}).

Despite these results, we acknowledge concrete limitations in this study. First, our evaluation relies on a discrete-event emulator calibrated to prior literature rather than physical CXL 3.0 Type-3 hardware, which remains scarce; the link and compute engine are each modeled as a single-server FCFS queue, a defensible but simplified model of a real interconnect and GPU that may under- or over-state contention effects at very high concurrency. Section~\ref{sec:real-model}'s real-model validation closes part of this gap -- real layer structure and real GPU-timed compute rather than a synthetic formula -- but the CXL link itself remains simulated throughout, since no physical CXL 3.0 testbed was available to us. Second, our approach currently focuses on static, single-model computation graphs where per-layer reuse frequency is either uniform (ordinary transformer blocks) or a known architectural constant (weight-tied embeddings); dynamic control flows such as Mixture-of-Experts routing -- where activation frequency is data-dependent and only observable online, not statically known -- are not modeled, and remain a genuine open problem for graph-aware pinning as presented here. Third, our earlier multi-tenant and application-level serving results (Sections~\ref{sec:multi-tenant-full}, \ref{sec:serving}) used a synchronized-burst arrival model rather than a sustained open-loop/Poisson arrival process; Section~\ref{sec:continuous-batching} now closes this gap directly with a genuine open-loop, iteration-batched evaluation, though it uses a small, purpose-built model (chosen so that tested arrival rates span below- and above-capacity regimes within a tractable run) and stylized 5-round decode length rather than a full production token budget, and its finding that continuous batching provides only marginal (${\sim}2\%$) throughput amortization is itself contingent on this engine's compute-bound cost model (Section~\ref{sec:scalability}) and may not generalize to memory-bound serving configurations where batching's fixed-cost amortization is more consequential. Fourth, Section~\ref{sec:sensitivity}'s hyperparameter and scale sweeps remain on synthetic workloads, not the real-model configuration of Section~\ref{sec:real-model}; combining the two -- sweeping $\gamma$, bandwidth, or tenant count on a real pretrained model -- is a natural next step we have not yet taken. As future work, we plan to extend CAMP to support dynamic control flows like Mixture-of-Experts (MoE), model genuine per-tenant scheduling and SLOs, combine the real-model and sensitivity-sweep evaluations, and conduct validation on emerging physical CXL 3.0 testbeds as they become available.
